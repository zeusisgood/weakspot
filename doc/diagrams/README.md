# 現行の挙動の図

[← 文書の案内に戻る](../README.md)

コードから描いた、今の挙動の図です（Mermaid。GitHub でそのまま表示される）。リファクタ（`common/` への切り出しなど）の前の基準にし、リファクタのあとに同じ挙動かを確かめるチェックリストとして使います。

| 図 | 中身 |
|---|---|
| [図 1　全体構成](01-overview.md) | パッケージどうしの依存と、Minecraft・Forge に依存するかの色分け |
| [図 2　ヒットの流れ](02-hit-flow.md) | 2a ヒット 1 回の流れ（共通）、2b 頭の上のコンボ・弱点のマークの配信、種類で違う箇所 |
| [図 3　状態遷移](03-states.md) | 3a 弱点の一生（ブロック・動物）、3a′ 照準のまわり、3b コンボ、3c 的当てのラウンド |
| [図 4　データの持ち場所](04-data.md) | 設定・統計・保存データの置き場所と、どちらを正とするか |

## 決まり

- **コードを正とする**。仕様書・`architecture.md` と食い違うところは、図をコードに合わせ、文書のほうを直す。
- 版の注記は書かない（今の挙動だけ）。
- クラス名・メッセージ名・設定キーは、コードの綴りのまま。
- 確信が持てないところは、図の注記に「要確認」と書く。
- コードの挙動を変えたら、関係する図も直す。

## 使い方（リファクタのあと）

1. 図 1: 新しいクラスの置き場所が、色分け（純粋・依存あり・クライアント専用）と合っているか。`server/` へ入る太い矢印が増えていないか。
2. 図 2: 2a の番号の順に、同じクラス（または移した先）が同じ順序で呼ばれるか。「種類で違う箇所」の表の各行が残っているか。
3. 図 3: 各状態に入る・出る条件が同じか（特に、消えるきっかけ・0 に戻すきっかけ・やめるきっかけ）。
4. 図 4: 正とするものが変わっていないか。保存のキー（`weakspot` / `total` / `guideGiven` など）と、`SyncedSettings` で送る項目が同じか（`WireCompatTest` も確かめる）。
