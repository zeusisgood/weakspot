# 弱点破壊 Mod 追加仕様書（v1.11.10）

`SPEC_v1.11.9.md`（Mod 1.11.8）に対する**パッチ**の仕様（文書とコードのコメントだけの整理）。ここに書かれていないことは、それと現行実装のままとする。
この仕様書は `doc/spec/SPEC_v1.11.10.md`。

- 対象: Minecraft Java Edition 1.12.2 / Forge 14.23.5.2860
- 前提: 1.11.8 がリリース済み、仕様書 1.11.9 の整理（PR #44）が `main` に取り込み済み
- 考え方（ユーザーとの相談）: 「コードには How、テストコードには What、コミットログには Why、コードコメントには Why not」（t-wada 氏）。**コードを読めば分かること（How）は文書に写さない**（写すと片方だけ古くなる。1.11.9 で `HitGate.onLogout`・「1.7.10」などの古い記述が見つかった）
- **PR を 2 つに分ける**（ユーザーの判断）
  - PR 1「文書の整理」: §1・§2・§4。この仕様書と `doc/spec/README.md` の 1 行もこちらに入れる
  - PR 2「1.11.10」: §3 とリリース。PR 1 が `main` に取り込まれたあと、`main` から切ったブランチで作る
- 遊び方・見た目・通信内容・設定・保存データ・動作は変えない

## 1. `doc/architecture.md` を「地図 + 理由」にする（PR 1。ユーザーの判断: 案 B）

### 1.1 残すもの

- **地図**: 機能・仕組みごとに、入口のクラス（両側・クライアント・サーバー・`common/`）と、使うイベント・メッセージ・保存のキー・設定の名前を 1〜3 行で
- **Why**: コードを読んでも分からない理由（例: クリックのたびにブーストを捨てる理由と issue #38、ヒットの間隔を `HitBudget` にした理由、`ServerFeatures` で古いサーバーに弱点を出さない理由、1 tick で壊れるブロックの扱い）
- **バニラの調べた結果**（バニラの側の話なので、この Mod のコードには出てこない）: 掘り終わりの保留が 1 枠・START に返事をしない、`blockRemoving` の判定式、エリトラの引き戻し（100 / 300）、`GuiContainer` がライティングを有効にしたまま戻る、`processPlayerDigging`、`isBreedingItem` など右クリックで動くアイテムの調べ方
- 次の節はほぼ Why なので、中身を残す（短くできる所だけ短くする）: 「クライアントを信じる範囲」「重要: サーバー側のブーストは時間枠ではない」「設定」の移行と読み直し
- **弱点の種類を足すときに直す所**の一覧（`CLAUDE.md` から指している）
- 通信のメッセージの番号と、運ぶ中身の一覧（`network/`）。互換性を確かめるときに使うため
- `ServerFeatures.since` / `PlayerText.clientSince` で分けている版（今は 1.11.2・1.11.3）

### 1.2 消すもの（How）

- クラスの中の処理の流れ・メソッドの呼ぶ順・フィールドの名前の並び・計算式の細部で、コードを読めば分かるもの（例: `AimSpots` の `beforeTick` / `afterTick` / `tickEnd`、`ComboHud` の描く順、`WeakSpotPlacer.layout` の式、`StatsScreen` のボタンの流れ、`BugReport` の見出しの並び）
- コードのコメントに同じ Why がすでにあれば、文書では繰り返さず、クラス名だけにする
- 迷ったら残す。意味が変わる書き換えはしない

### 1.3 形

- 今の見出し（「全体」「クライアントを信じる範囲」「重要: …」「設定」）と、「全体」の中の分け方（`common/`・`RightClickTargets`・`client/`・共通の部品・`network/`・`server/`）は変えない
- 量の目安は約 1〜1.5 万字（今は約 5 万字）。目安なので、残すものを削ってまで合わせない

## 2. `CLAUDE.md` の How を消す（PR 1）

- 決まり（これからどうするか）は変えない。How（コードの中身の説明）だけを消す
- 対象:
  - 「アーキテクチャの約束事」の「共通の部品」の行の、クラス名の長い並び → 「共通の部品があるものは、それを使う。一覧は `doc/architecture.md` の「共通の部品」」の形にする（`HitGate`・`HitBudget` など特に大事なものは、ほかの行に出てくるので残る）
  - 「サーバー側の採掘のブーストは時間枠ではない」の行の、判定式の説明（「破壊完了の瞬間に…`BoostMath`」）→ 決まり（「破壊速度まわりを変えるときは、クライアント（積算）とサーバー（瞬間判定）の結果が一致するかを確かめる。仕組みは `doc/architecture.md` の「重要」の節」）だけにする
  - ほかにも、決まりの文の中の長い仕組みの説明（カッコの中のクラス名の並びなど）があれば、決まりが読めなくならない範囲で短くする
- 版の注記（「1.11.6。」など）は、1.11.8 §3 で対象外にしたまま変えない

## 3. コードのコメントの整理（PR 2。ユーザーの判断: 案 B）

### 3.1 消すもの

- **版の注記**: 「（1.3.0）」「（1.8.6。論理サーバー）」の「1.8.6。」のような、いつ足したかだけの版の番号（経緯はコミットログ・`CHANGELOG.md`・仕様書にある）
- **前の形の説明（経緯）**: 「1.5.4 で 3〜8 から広げた」「1.11.6 から HitBudget」「〜までは…だった」「試してもらったあとに変えた」。**カッコの中の理由（Why）は残す**（例: 「1.5.4 で 3〜8 から広げた（近すぎて照準を動かさずに当たったため）」→「近すぎると、照準を動かさずに当たるため」）

### 3.2 残すもの

- Why / Why not、単位（度・tick・ブロック）、範囲、引数の約束（「0 ならどちらでもよい」など）、どちらの側で動くか（両側・論理サーバー・物理サーバーでは呼ばれない など）
- **動作に関わる版の番号**:
  - `ServerFeatures.since("1.x.y")` / `PlayerText.clientSince` / `PlayerText.of` の `since` のまわりの説明（どの版から使う・送るか）
  - 版の番号そのものが動作を決めている所（`targetGiftVersion` がない人は 1.11.0 とみなす、など）
  - 古い保存のキー・設定を読む所は、版を消して「古い版のキー」の形にしてよい（どの版かが読み方に関わるなら残す）
- `@Config.Comment`（設定ファイルと設定画面に出る説明）は対象外（もともと版の注記を書かない決まり）
- テストのコード（`src/test`）も同じ方針で直す。テストの名前・中身は変えない

### 3.3 やり方

- 機械的に探す: コメントの中の `1\.[0-9]+\.[0-9]+`・「までは」「に変えた」「から変更」「以前は」「だった」「試してもらった」
- 1 つずつ読み、3.1・3.2 で直す。迷ったら残す
- How の言い直し（シグネチャを読めば分かる Javadoc）は、この PR では消さない（案 C は見送り。移植で書き直すときに自然に減る）
- 量の目安（調べた時点）: コメントは約 2,930 行（コードの約 14%）、版の番号を含むコメントの行は約 480、経緯の言い回しは約 40 か所
