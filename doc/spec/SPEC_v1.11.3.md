## 0. バージョンと互換性

- バージョンは 1.11.2 → **1.11.3**（`build.gradle` の `version` と `WeakSpotMod.VERSION`）
- 通信内容は変わらない。今の `OtherComboMessage`（エンティティの ID とコンボ数）を、本人にも送るだけ（形も意味も同じ「そのプレイヤーのサーバーでのコンボ数」）。設定の項目は足さない。`configVersion` は上げない
- サーバーは、1.11.3 より古いクライアントには本人宛ての `OtherComboMessage` を送らない（§3）。クライアント側の受け取りは `ServerFeatures.since("1.11.3")` で囲む
- 内容は 1 つ: クライアントとサーバーのコンボを揃える（`doc/diagrams/README.md` の要確認 2・3、`doc/roadmap.md` の TODO）

## 1. やりたいこと（ユーザーの判断）

- 今は、クライアント（`OwnHits.STREAK`）とサーバー（`ServerStats` の `HitStreak`）が別々にコンボを数えている。サーバーがヒットを受け付けないと（間隔・条件・収穫の失敗（保護された土地など）・掘る前の予約を捨てたとき）、クライアントの表示と音だけが増え、数がずれる
- **サーバーの数を正とし、ずれたらクライアントの表示を直す**（案 B1a）。掛け数・節目・告知・進捗は、もともとサーバーの数で決まるので変えない。直るのは見た目（コンボの表示・次のヒット音の高さ・「MAX n」）だけ
- 鳴ってしまったヒット音と、出てしまった節目の演出は取り消さない
- ラグでサーバー側だけコンボが途切れた（サーバーで 1 から数え直した）ときも、クライアントをサーバーの数に合わせる

## 2. ずれの見つけ方（サーバー。`HitHandlers.onHit`）

- `HitMessage` の `streak`（クライアントのヒット後のコンボ数）を、処理のあとのサーバーの数と比べる。比べるのは `HitHandlers.onHit` の 1 か所（全種類が通る）
- サーバーの数 = `ServerStats.streak(player).count(now)`（途切れていれば 0）＋ そのプレイヤーの掘る前の予約（`ServerBoostTracker.RESERVED`）があれば 1（クライアントはもう数えていて、サーバーは掘り始めたら数えるため）
- 違っていれば、そのプレイヤーに「直しが要る」印を付ける（すぐには送らない。§3）
- 予約を捨てたとき（時間切れ・上書き）は、その場では見つけない。次のヒットで比べたときに見つかる（予約の時間切れを見張る仕組みは足さない）
- 的当て（`TargetRounds`）のヒットは種類ではないので対象外（コンボに数えない今のまま）
- 処理を後回しにする種類があれば（ヒットの受け付けがメッセージの処理の中で終わらないもの）、実装のときに調べて、その種類は比べない

## 3. 直しの送り方（サーバー。`ComboRelay`）

- 印の付いたプレイヤーについて、`ServerTickEvent` の END で、**最後にヒットを受け取ってから 3 tick 以上たっていたら**、本人に `OtherComboMessage(自分の ID, §2 のサーバーの数)` を送り、印を消す（当て続けている間は送らない。届く前に次のヒットを送っていると、直すと 1 つ足りなくなるため）
- 本人宛ては、1 人あたり 4 tick に 1 回まで（`ComboRelay.MIN_INTERVAL_TICKS` と同じ）
- 送る相手は、`PlayerText.clientVersion(player)` が 1.11.3 以上のときだけ（不明なら送らない）
- ほかのプレイヤーへの今の送り方（変わったとき・4 tick に 1 回まで・32 ブロック以内）は変えない
- 3 tick は実装の目安（試してもらって決め直す）

## 4. 直し方（クライアント）

- `ClientProxy.onOtherCombo` で、ID が自分（`mc.player.getEntityId()`）なら `OtherCombos` ではなく、自分のコンボの直しとして扱う（`ServerFeatures.since("1.11.3")` が false なら今どおり何もしない）
- 自分の最後のヒット（`OwnHits` の連続ヒットの最後の tick）から **3 tick 以上たっているときだけ**直す。たっていなければ捨てる（ずれが残っていれば、次のヒットでサーバーがまた見つけて送る）
- 直すときは、`HitStreak` の数だけを書き換える（最後のヒットの tick は変えない。途切れるまでの残り時間のバーもそのまま）。数字は**黙って書き換える**（弾み・音・節目の演出・色の段階の演出は出さない）
- 0 が届いたら、途切れたときと同じく 0 に戻す。ただし「MAX n」は出さない（サーバーでは途切れていたため）
- `HitStreak` に数を書き換える関数を足す（`common/`。単体テストも）

## 5. 改造クライアントへの備え

- **片道だけ**: サーバーは `HitMessage` の `streak` を、§2 で比べるためと、今のほかのプレイヤーのヒット音の高さにしか使わない。サーバーの数をクライアントの数に合わせることはしない
- **間引き**: 直しの送信は §3 のとおり 1 人あたり 4 tick に 1 回まで。でたらめな `streak` を付けたヒットを大量に送られても、サーバーの送信は増えない
- 接続のときの Mod の一覧の版は、改造クライアントなら書き換えられるが、困るのは本人だけ（直しが届かない、または古いクライアントに届いて自分の頭上に表示が出る）
- 不正対策の方針は今のまま（ほかの種類は塞がない。的当ての案 A は保留。`doc/roadmap.md`）

## 9. ユーザーに確認してもらうこと

- 保護された土地（またはスポーン保護の中）で収穫の弱点に当てると、コンボの表示が一瞬増えても、少し手を止めるとサーバーの数に戻る
- 普通に当て続けている間は、数字が戻ったり跳んだりしない（直しのせいでちらつかない）
- 掘る前の採掘の弱点に当てて掘り始めたときも、数がずれない。当ててから掘らずに 1 秒以上待ったとき（予約が捨てられる）は、次にどこかで当てて手を止めると 1 つ減る
- ほかのプレイヤーの頭上の「n HIT」は今どおり
- 古いクライアント（1.11.2）で 1.11.3 のサーバーに入っても、自分の頭上に何も出ない
