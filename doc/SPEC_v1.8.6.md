# 弱点破壊 Mod 追加仕様書（v1.8.6・下書き）

> 下書き。ユーザーが「実装」と言うまで実装しない。

`SPEC_v1.8.5.md`（Mod 1.8.5）に対する**パッチ**の仕様。ここに書かれていないことは、それと現行実装のままとする。
仕様書は、リポジトリの `doc/` ディレクトリに置く（この仕様書は `doc/SPEC_v1.8.6.md`）。

- 対象: Minecraft Java Edition 1.12.2 / Forge 14.23.5.2860
- 前提: 1.8.5 がリリース済み
- この仕様書の内容は、Mod のバージョン **1.8.6** として、リリースする

---

## 0. バージョンと互換性

- バージョンは 1.8.5 → **1.8.6**（`build.gradle` の `version` と `WeakSpotMod.VERSION`）
- 中身は、**処理の整理（リファクタ）** と、**クリエイティブでもすべての弱点を出す**（下の 2）
- **通信内容・保存データ・設定は変わらない**。1.8.x 同士は、そのまま接続できる
  - 統計（`StatsMessage`）と設定（`SettingsMessage`）の送る中身は、1 バイトも変えない（下の 1.3・1.4）
  - 保存のキー（`PlayerPersisted` の `weakspot` の中）は、今の名前のまま
- 1.8.5 以前のサーバーにつなぐと、クリエイティブの弱点は今までどおり（サーバーが受け付けない種類は、クライアントも出さない。`ServerFeatures.since("1.8.6")`）

## 1. 処理の整理（ユーザーの判断: A1〜A6 をまとめて。A7 は後回し）

遊び方は変えない。1 つずつコミットを分ける（1 つずつ戻せるように）。

### 1.1 サーバーのヒットの前置きをまとめる（A1）

- 今: `AnimalHits`・`BowHits`・`EatHits`・`EnchantHits`・`FishingHits`・`MeleeHits`・`MoveHits`・`PortalHits`・`SleepHits`・`ThrowHits`・`VehicleHits`・`RightClickHits`・`ServerBoostTracker` が、それぞれに「オンか（`ServerSwitches.isEnabled(player, kind)`）・観戦モードでないか・前のヒットからの間隔（設定の間隔 − 2 tick）・プレイヤーごとの最後の tick」と、ログアウトの後片付けを持つ
- 新: `server/HitGate` にまとめる
  - `HitGate.pass(player, kind, minIntervalTicks)`: オン・観戦モードでない・間隔を満たすなら、最後の tick を記録して true。種類ごと・プレイヤーごとの最後の tick を持つ
  - 種類ごとの条件（弓を引いているか、ゲートの中か、など）は、今までどおり各クラスに残す
  - ログアウトの後片付けは `HitGate` がまとめて行う。各クラスのプレイヤーごとの記憶（溜め・残り時間など）も、`HitGate.onLogout` から呼ぶ 1 か所にまとめ、付け忘れを防ぐ
- 間隔の数（2 tick 甘く）、判定の順番、受け付けたときの処理は変えない

### 1.2 ヒットの振り分けを表にする（A2）

- 今: `HitMessage` のハンドラーが、種類ごとの `if … else if` を 14 段持つ
- 新: 種類 → 処理の表（`server/HitHandlers`。`HitKind` ごとに 1 行登録）。登録のない種類は無視する（今と同じ）

### 1.3 統計を種類ごとの配列で持つ（A3）

- 今: `MiningStats` は種類ごとの数を 17 個の変数（`growthHits` … `portalHits`、近接は `critHits`）で持ち、`recordKindHit` と `count` の `switch`、`StatsMessage` の送受信、`ServerStats` の保存で、1 項目ずつ手で書いている
- 新: `MiningStats` は `HitKind` ごとの数を配列で持つ（採掘は今までどおり `hits` と、短縮した時間などの採掘だけの項目）
  - 保存のキーは、種類ごとの表（`MiningStats.SAVE_KEYS`。例 MELEE → `critHits`）で、今の名前のまま
  - `StatsMessage` の送る順番は、今の順番の表（`maxStreak` が途中に入る今の並び）で、1 バイトも変えない
- 単体テスト: 今の送り方・読み方と同じバイト列になることを、決まった値で比べる（今の実装で作ったバイト列をテストに書いておく）

### 1.4 送る設定を 1 つの一覧から回す（A4）

- 今: `SyncedSettings` の 72 項目を、`fromConfig`・`write`・`read` の 3 か所に、1 つずつ同じ順番で手で並べている
- 新: 項目の一覧（名前・型・`WeakSpotConfig` からの読み方）を 1 つにし、3 つの処理はその一覧を回す。送る順番は今のまま
- 単体テスト: 1.3 と同じく、今の実装と同じバイト列になることを比べる（MC のクラスを読み込めずテストにできないときは、変更前後の jar で同じ値を書いたバイト列を比べる小さなプログラムで確かめる）

### 1.5 照準のまわりの弱点の共通の土台（A5）

- 今: はしご・走り・食事・ゲート・投げる物・近接・エリトラ・乗り物の各クラス（`client/*Spot`）が、同じ形（毎 tick 出す条件を見る → `HudSpot` に出させる → 当たったら音・コンボ・通知 → 種類ごとの効果）を、それぞれに書いている。弓（`BowSpot`）は `HudSpot` を使わず、描き方・当たり判定・出し直しを自前で持つ
- 新: 共通の土台 `client/AimSpotKind`（出す条件・出し方（全方向／上下だけ／左右だけ）・当たったときの種類ごとの処理・ゲージ、だけを各種類が書く）を作り、8 種類と弓を載せる
  - 弓の過剰チャージの目盛り、乗り物のボートの向きについて回る処理、エリトラの交互だけの決め方は、各種類の中に残す
  - 釣り（水面の位置に出す）は、形が違うので今のまま
- 見た目・当たり判定・位置の決め方（1.8.1・1.8.2）は変えない

### 1.6 コンボの掛け数の名前（A6）

- 今: どの種類も、コンボの掛け数を `MachineComboBoost.factor` で求めている
- 新: `common/ComboFactor.factor(連続ヒット数)` に切り出す。`MachineComboBoost` はそれを使う。数は変えない（`ComboFactor` の単体テストは、今の `MachineComboBoost.factor` のテストを移す）

## 2. クリエイティブでも、すべての弱点を出す（ユーザーの判断: b）

- 今: 採掘・成長・機械・動物・収穫・睡眠・エンチャントはクリエイティブでも出るが、弓・食事・釣り・近接・乗り物・はしご・走り・エリトラ・投げる物・ゲートは出ない（クライアントもサーバーも止めている）
- 新: クリエイティブでも、すべての種類を出す（試すときに便利なため）。**観戦モードでは、今までどおり出さない**
- クライアントは `ServerFeatures.since("1.8.6")` のときだけクリエイティブでも出す（1.8.5 以前のサーバーは受け付けないので、出ても何も起きない食い違いを防ぐ）
- クリエイティブでは食べ物を食べられない（空腹にならない）ので、食事の弱点は、いつでも食べられる物（金のリンゴなど）と飲み物のときだけ出る。これはバニラどおり

## 3. 統計の `critHits` の説明（B3）

- 保存のキー `critHits` の中身は、1.8.0 から「近接の弱点に当てた回数」（それまではクリティカルにした回数）。キーは互換のため変えない
- コード（1.3 の保存のキーの表）と README の統計の表に、そのことを一言書く
